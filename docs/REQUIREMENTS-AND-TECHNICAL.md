# 下一站：纯前端复刻需求与技术说明

## 目标与范围

以现有旅行网站的最新本地前端源码为基础，交付可以静态展示和交互的桌面作品，用于仅接收前端项目的制作或展示平台。保留地图、票券、旅行手账、房间投票和表单设计。原生产站独立保留，不在本次交付中重新部署。

交付不包含真实用户信息、原站房间数据、服务器代码、数据库、访问密钥和后台配置。示例人物与房间由浏览器首次打开时生成。

## 原站依赖及处理

| 原站依赖 | 本次替代 |
| --- | --- |
| 推荐服务配置状态 | 本地固定演示状态 |
| 行程生成和换站 | `FrontendDemo.itinerary()` 返回预置模板或占位草稿 |
| 对话与城市建议 | 本地规则匹配固定文案，不执行任意自然语言规划 |
| 在线查价、住宿检索 | 费用说明和手动填写，不伪造实时结果 |
| 房间接口、令牌与数据库 | `FrontendDemo.room()` 修改 localStorage 中的示例对象；本地标识不是安全鉴权 |
| 在线房间轮询 | 去除定时网络轮询，操作后即时更新，同源标签页可读取本地存储变化 |
| 动态图片查询 | 仅使用随包提供的城市图片目录；未收录时显示空状态 |
| 地图 JSON 请求 | JS 变量直接装载本地数据，支持直接打开文件 |
| 平台运行时集成 | 已移除，不要求特定平台的工具运行时 |

## 目录职责

- `index.html`：唯一页面入口；按顺序载入本地样式、脚本和素材。
- `app.js`：主页面、导航、地图、收藏、个人行程和弹窗交互。
- `frontend-demo.js`：浏览器本地适配层，提供示例行程、固定问答、本地房间读写和初始数据。
- `rooms.js` / `room-tools.js`：房间展示、方案操作、日历、清单、账单和旅行当天。
- `trip-chat.js`：对话界面，调用本地示例适配器。
- `plan-state.js` / `plan-features.js` / `itinerary-details.js`：行程状态、费用计算、时间线与编辑辅助。
- `city-highlights.js` / `dart-picker.js` / `data.js`：城市照片、抽选规则和内置六城示例。
- `assets/`：地图数据、城市目录、照片、安安形象、D3 和图标脚本。
- 多个 `.css` 文件：沿用现有页面设计；`frontend-demo.css` 仅追加演示范围标识。

不需要构建服务。源码 ZIP 解压后即是静态网站根目录。单文件 HTML 将这些文件内嵌，运行时用浏览器 Blob URL 装载素材和内联脚本；没有请求后端。

## 状态与业务行为

本机数据使用独立的 `nextstop-frontend-` 前缀，不读取原站的个人存储。主要存储包括个人候选/计划、房间入口、本地房间对象和初始化标记；编辑中的表单可使用 sessionStorage 暂存。

个人行程与房间方案分别保存。用户选择把个人方案带入本地房间后，才建立本地对应关系。费用记录与预算估算分开，估算不计作实际支付。房间结算使用原前端的整数分金额分摊逻辑。

修改房间行程会保留历史版本、增加版本号并清空原确认。修改实际花费不修改路线版本。关闭房间后可查看内容，重新开放后才能继续修改。本地版本检查只是演示交互的状态保护，不能替代服务器并发控制和权限校验。

## 前端限制

- 不提供真实身份验证、跨设备存储、多人在线同步、消息推送和可靠数据备份。
- 不提供模型服务、动态图片搜索、实时酒店/交通/门票/天气数据或付款预订。
- 第三方地图、照片署名等链接只有点击后才会打开外站；页面自身运行不依赖这些链接。
- 本地文件链接只适用于自己的设备。发布到静态托管后可分享页面和只读快照，但每个人的 localStorage 仍各自独立。
- 主要验证环境为桌面 Chrome。严格禁止内联脚本或 Blob 的平台可能需要使用多文件源码形式，而不是单文件 HTML。
- 浏览器禁用 JavaScript、拒绝站点存储或空间不足时，交互/持久化可能受限；这不是可用于正式多人业务的生产后端替代品。

## 验收要求

- 静态打开后地图、照片和界面完整显示；保留登机牌首页与旅行票券视觉。
- 无运行时业务接口请求，不要求后端启动或配置密钥。
- 候选、投票、表单、行程和账单的核心操作可在本机完成，刷新保留。
- 对示例推荐、演示房间和实时能力缺失做可见说明。
- 不把原站实际用户数据打包；不把示例包装成实时旅行建议。
